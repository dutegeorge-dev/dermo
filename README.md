# Сайт ООО ТЛК БАРС — каркас

Статический сайт-каркас торгово-логистической компании на **Eleventy (11ty) + Tailwind CSS + TypeScript**.

> Это **каркас**: страницы созданы как пустые шаблоны с корректными URL, мета-тегами, разметкой, sitemap/robots, аналитикой и рабочими формами заявок (лиды уходят в Bitrix24 и дублируются в Telegram). Контентное наполнение — отдельный этап (через Decap CMS).

## Технологии

- **Eleventy 3** — генератор статики (конфиг на TypeScript).
- **Tailwind CSS 3** — стили, сборка через PostCSS (autoprefixer + cssnano на проде).
- **Nunjucks** (`.njk`) — шаблонизатор.
- **TypeScript** (`strict: true`) — конфиг 11ty, дата-файлы, клиентский JS. Серверный TS исполняется через `tsx`, клиентский компилируется в JS через **esbuild**.
- **Decap CMS** — админка по `/admin/`.

## Требования

- Node.js LTS (см. `.nvmrc` — версия 20).

## Установка

```bash
nvm use          # при наличии nvm
npm install
cp .env.example .env   # заполнить при необходимости (можно оставить пустым для dev)
```

## Команды

| Команда             | Назначение                                                                 |
|---------------------|----------------------------------------------------------------------------|
| `npm run dev`       | Локальная разработка с hot-reload (11ty serve + watch Tailwind + watch TS). |
| `npm run build`     | Продакшн-сборка в `_site/` (минификация, purge CSS, sitemap/robots).        |
| `npm run typecheck` | Проверка типов `tsc --noEmit` (без ошибок).                                 |
| `npm run clean`     | Очистка каталога сборки `_site/`.                                           |
| `npm run cms`       | Локальный сервер Decap CMS (`decap-server`) для админки без хостинга.        |
| `npm run server`    | Бэкенд-обработчик заявок (порт 3000) → лиды в Bitrix24 + Telegram.           |

После `npm run dev` сайт доступен на `http://localhost:8080`, обработчик заявок — на `http://localhost:3000` (поднимается тем же `npm run dev`).

## Переменные окружения

Реальные ID не хранятся в репозитории — задаются через `.env` (см. `.env.example`):

- `SITE_URL` — базовый URL (canonical/OG/sitemap).
- `YM_COUNTER_ID` — Яндекс.Метрика (пусто → счётчик не подключается).
- `GA4_ID` — Google Analytics 4 (пусто → тег не подключается).
- `YANDEX_VERIFICATION`, `GOOGLE_VERIFICATION` — мета-теги верификации.
- `BITRIX_WEBHOOK_URL` — входящий вебхук Bitrix24 для заявок (**секрет**, см. раздел «Формы и заявки в CRM»).
- `LEAD_API_URL`, `LEAD_PORT`, `LEAD_ALLOWED_ORIGINS` — адрес, порт и CORS-allowlist обработчика заявок.
- `RATES_API_URL`, `RATES_TTL_MS` — адрес эндпоинта курсов ЦБ для калькулятора и время их кэширования (см. «Калькулятор доставки»).
- `TELEGRAM_BOT_TOKEN` (**секрет**), `TELEGRAM_CHAT_ID` — дубль заявки в Telegram (необязательно).

## Формы и заявки в CRM (Bitrix24) + Telegram

Заявки со всех форм сайта уходят в Bitrix24 и дублируются в Telegram через собственный бэкенд-обработчик в каталоге `server/` — без сторонних сервисов и без зависимостей (только Node).

**Как это устроено:**

1. Браузер: `src/assets/ts/main.ts` валидирует поля и шлёт `POST` JSON на эндпоинт из атрибута `data-lead-endpoint` (значение — `site.leadApiUrl`, переменная `LEAD_API_URL`).
2. Бэкенд: `server/index.ts` слушает порт 3000 (`LEAD_PORT`), путь `/api/lead` (`LEAD_PATH`); там же живёт `GET /api/rates` для калькулятора.
3. `server/lead.ts` разбирает заявку и собирает поля лида; `server/bitrix.ts` вызывает `crm.lead.add` по входящему вебхуку портала.
4. `server/telegram.ts` дублирует заявку в чат менеджера со ссылкой на карточку лида.

**Настройка:**

1. В Bitrix24: «Приложения → Разработчикам → Другое → Входящий вебхук», права — `crm`.
2. Полученный URL положить в `.env` (файл в `.gitignore`, в репозиторий не попадает):

   ```
   BITRIX_WEBHOOK_URL=https://<портал>.bitrix24.ru/rest/<user_id>/<token>/
   ```

   Можно вставить и полную ссылку на метод с query-строкой — обработчик сам обрежет лишнее.
3. Уведомления в Telegram (необязательно): создать бота у [@BotFather](https://t.me/BotFather), узнать свой ID у [@userinfobot](https://t.me/userinfobot) и добавить в `.env`:

   ```
   TELEGRAM_BOT_TOKEN=<токен бота>
   TELEGRAM_CHAT_ID=<ваш ID>          # несколько получателей — через запятую
   ```

   Каждый получатель должен один раз написать боту `/start` — иначе Telegram не даст боту начать переписку. Без этих переменных заявки всё равно идут в CRM, просто без дубля в чат.
4. `npm run dev` (или `npm run server` отдельно) — и формы работают.

**Что попадает в лид:** `TITLE` («Заявка с сайта — <груз>»), `PHONE` / `EMAIL` / `IM` (телефон, почта или Telegram — тип определяется автоматически по введённому контакту), `SOURCE_ID` (по умолчанию `WEB`), `SOURCE_DESCRIPTION` (страница), UTM-метки (`UTM_SOURCE` и др., подхватываются из URL и переживают переходы по сайту), а также `COMMENTS` — груз, объём/вес, исходная строка контакта, страница, реферер, язык, форма и отметка о согласии на обработку ПДн (152-ФЗ) с временем и IP.

**Уведомление в Telegram** приходит на каждую заявку: контакт (телефон кликабельный), груз, объём, страница, форма, UTM и ссылка на карточку лида в CRM. Если портал недоступен, вместо этого приходит предупреждение «заявка НЕ попала в CRM» с теми же данными — контакт клиента не теряется. Отправка идёт уже после ответа браузеру, поэтому недоступный Telegram не тормозит форму и не превращает принятую заявку в ошибку.

**Защита:** обязательное согласие на обработку ПДн, honeypot-поле, ограничение частоты по IP (`LEAD_RATE_LIMIT` заявок за `LEAD_RATE_WINDOW_MS`), лимит размера тела, CORS-allowlist (`LEAD_ALLOWED_ORIGINS` + `SITE_URL`), таймаут и повтор запроса к порталу. Заявки, которые не удалось отдать в CRM, дописываются в `logs/leads-failed.jsonl`, чтобы не потерялись. Токены вебхука и бота в логи не пишутся.

**Прод:** статика раздаётся как обычно, а `server/` запускается рядом (systemd/pm2/Docker) и проксируется на тот же домен по `/api/lead` — тогда в окружении сборки достаточно `LEAD_API_URL=/api/lead`, и CORS не нужен.

## Калькулятор доставки и таможенных платежей

Страница `/calculator/` (кнопки «Рассчитать» в шапке ведут на неё — `site.calculateUrl`) считает сборную доставку из Китая, пошлину и НДС и отправляет расчёт заявкой в Bitrix24. После отправки — отдельная страница благодарности `/calculator/spasibo/` (`noindex`, вне sitemap), чтобы конверсия калькулятора считалась отдельно от общей `/spasibo/`.

**Единый источник правды — `server/calc.ts`.** Тарифы (ЖД 150 $ оформление + 160 $/куб.м, авто 150 $ + 330 $/куб.м), комиссия компании, лимит 300 кг/куб.м, список городов, ставки НДС и сами формулы описаны там один раз и используются тремя сторонами:

- `src/_data/calculator.ts` отдаёт конфиг в вёрстку (`src/pages/calculator.njk`) — селекты, карточки тарифов и тексты пояснений строятся из него;
- `src/assets/ts/calculator.ts` импортирует тот же модуль и считает в браузере на каждый ввод;
- `server/index.ts` пересчитывает заявку перед отправкой в CRM — в лид попадают суммы, посчитанные нами, а не пришедшие из браузера.

Менять тарифы, города или ставки НДС нужно **только** в `server/calc.ts`: пересборка подхватит их и на странице, и на бэкенде.

**Тарифы и норма загрузки — внутренние данные и на странице не публикуются.** Посетитель видит сроки доставки, границу применимости (до 8 куб.м) и итоговые суммы, но не цену за кубометр, не лимит 300 кг/куб.м и не объём к оплате. В детализации и в поясняющих блоках этих чисел тоже нет — там только принцип («плотный груз считается по весу»). Если правите страницу, не возвращайте `method.rate` и `weightPerCbm` в вёрстку. Полный расчёт с тарифом остаётся в карточке лида — он для менеджера. Обратите внимание: сами константы попадают в клиентский бандл (расчёт идёт в браузере), и тариф за куб при желании выводится делением показанной стоимости доставки на объём — «спрятано» здесь означает «не опубликовано», а не «недоступно технически».

**Формулы:**

1. Расчётный объём = `max(объём; вес / 300)` — лёгкий груз оплачивается по объёму, тяжёлый по весу.
2. Доставка = разовый сбор за оформление (bill list, 150 $) + расчётный объём × тариф за куб. Первый кубометр поэтому стоит 310 $ по ЖД и 480 $ авто, каждый следующий — 160 $ и 330 $.
3. Стоимость товара в долларах = цена в юанях × кросс-курс ЦБ (курс юаня ÷ курс доллара).
4. **Таможенная стоимость = стоимость товара + половина стоимости перевозки.** При нескольких товарах доля перевозки делится между ними пропорционально цене — у каждого своя ставка пошлины и НДС, общей суммой обойтись нельзя.
5. Пошлина = таможенная стоимость × ставка. НДС = (таможенная стоимость + пошлина) × ставка НДС.
6. Комиссия ТЛК БАРС — фиксированная: 700 $ при стоимости товара меньше 10 000 $ и 1000 $ от 10 000 $ (`commission` в `server/calc.ts`).

Итог «под ключ» = товар + доставка + пошлина + НДС + комиссия.

**Города.** Калькулятор считает только до Москвы: тариф на другие направления зависит от плеча по России, поэтому под селектом стоит примечание со ссылкой на форму заявки — маршрут и стоимость туда считает менеджер. Появятся тарифы по городам — добавьте их в `cities` (`server/calc.ts`) и учтите в расчёте доставки.

**Курсы валют — `GET /api/rates`** (`server/rates.ts`, путь настраивается `RATES_PATH`). Источник — ЦБ РФ: основной канал `cbr-xml-daily.ru`, резервный — официальный XML `cbr.ru`. Курс кэшируется в памяти на `RATES_TTL_MS` (по умолчанию 6 часов — ЦБ публикует его раз в сутки) и дублируется в файл `RATES_CACHE_FILE`, чтобы пережить перезапуск службы. Если ЦБ недоступен, эндпоинт отдаёт последние известные курсы с флагом `stale`, и страница честно предупреждает об этом; если курсов нет вообще — 503, калькулятор считает только доставку. Курсы нигде не хардкодятся. Адрес эндпоинта попадает в вёрстку из `RATES_API_URL` (атрибут `data-rates-endpoint`), на проде — `/api/rates`.

**Заявка с калькулятора** уходит тем же `POST /api/lead`, но с блоком `calc` (город, способ, вес, объём, товары со ставками) и курсами, которые видел посетитель. Заголовок лида — «Заявка с калькулятора», в `COMMENTS` попадает полная детализация расчёта, в Telegram — краткая сводка.

**Честность расчёта.** На странице заметно указано: расчёт предварительный, для сборных грузов до 8 куб.м, погрешность 10–15 %, итог не является офертой; ставки пошлины и НДС зависят от кода ТН ВЭД и требуют подтверждения таможенным декларантом. Базовая ставка НДС в РФ с 01.01.2026 — 22 % (ФЗ от 28.11.2025 № 425-ФЗ), в селекте также 10 % и 0 %. **Если ставки изменятся — правьте `vatRates` в `server/calc.ts`.**

## Контент: блог и кейсы (Markdown, мультиязычно)

Статьи блога и кейсы пишутся в Markdown и рендерятся на читательском шаблоне (правое sticky-оглавление строится автоматически из заголовков `##`/`###`).

- Файлы: `src/blog/<slug>.<lang>.md` и `src/kejsy/<slug>.<lang>.md`, где `lang` ∈ `ru`/`en`/`zh`.
- **Русский обязателен**; `en`/`zh` опциональны. Если перевода нет — на языковой версии показывается русский контент (фолбэк, без 404). URL: `/blog/<slug>/`, `/en/blog/<slug>/`, `/zh/blog/<slug>/` (аналогично `/kejsy/`).
- Front matter статьи: `title`, `date`, `description`, `cover`, `related_service`, `draft`; у кейса дополнительно `result`. Черновики (`draft: true`) не публикуются и скрыты из витрин.
- Чтение и рендер Markdown собраны в `src/_data/library.ts` (фолбэк, автоякоря заголовков, списки витрин, обратная связка услуга→статья). Сырые `.md` исключены из обработки шаблонов; страницы генерируются пагинацией (`src/blog-pages.njk`, `src/kejsy-pages.njk`).
- **Перелинковка**: `related_service` в статье/кейсе → блок «закажите у нас» со ссылкой на услугу; обратно на странице услуги — ссылка на привязанную статью. Ссылки на ненаписанное скрыты.
- Витрины `/blog/` и `/kejsy/` (локализованные) — карточки с обложкой, датой/итогом, новые сверху.

## Фото: оптимизация и lazy-loading

Подключён `@11ty/eleventy-img`. Шорткод `{% image "путь", "alt", "sizes", "css" %}` на сборке делает ресайз, конвертацию в **AVIF + WebP + исходный формат** и отдаёт `<picture>` с `srcset`, `loading="lazy"` и `width`/`height` (без сдвига layout — CLS). Применяется к обложкам блога/кейсов и доступен для любых фото по сайту. Источник — `src/assets/img/` (загруженные через CMS — в `src/assets/img/uploads/`).

### Замена фото-плейсхолдеров из админки

Структурные фото сайта (hero услуг/товаров/городов, виды товаров, команда, флагманы, контакты) стоят плейсхолдерами. Чтобы заменить любое из них **без правки кода и без переименования файлов**, в Decap есть коллекция **«Фотографии сайта»**, сгруппированная по разделам (Главная, Услуги, Товары, Города, О компании и команда, Торговля, Контакты). Каждый слот — отдельное поле-картинка с человекочитаемой подписью (напр. «Москва — hero (4:3)»).

Как это работает: карты «ключ плейсхолдера → путь к фото» лежат в `photos/*.json` (их и редактирует Decap). При сборке шорткод `image` для каждого плейсхолдера проверяет эти карты: если для слота задано фото — берёт его, иначе — исходную заглушку. Загруженное фото автоматически проходит оптимизацию (AVIF/WebP, lazy). **Имя загружаемого файла значения не имеет** — привязка идёт по слоту, а не по имени. Обложки и фото внутри статей/кейсов редактируются прямо в записи (поле «Обложка» и вставка в тексте), а не через эту коллекцию.

## Decap CMS

Админка — `/admin/`.

**Локальный режим (без хостинга):** в конфиге включён `local_backend: true`. Запуск:

```bash
npm run dev      # dev-сервер сайта
npm run cms      # в отдельном терминале: npx decap-server
```

Открыть `http://localhost:8080/admin/` — правки пишутся прямо в файлы проекта без логина.

Коллекции: блог, кейсы (мультиязычные — `i18n: multiple_files`, отдельный файл на язык), товарные страницы. Загруженные фото попадают в `media_folder` (`src/assets/img/uploads`), откуда их подхватывает система оптимизации. Боевой бэкенд (`git-gateway`) оставлен заглушкой; после деплоя — Netlify Identity + Git Gateway либо `github`/`gitlab` backend (структура коллекций совместима).

## Хостинг

Сайт статический (каталог сборки `_site/`, команда `npm run build`), но формам нужен живой обработчик заявок. Поэтому вариантов два:

- **Статика/CDN (Netlify, Vercel)** — обработчик придётся разместить отдельно и указать его абсолютный адрес в `LEAD_API_URL`, добавив домен сайта в `LEAD_ALLOWED_ORIGINS` (нужен CORS).
- **Свой сервер с nginx** — статика, `/api/lead` и `/api/rates` живут на одном домене, CORS не нужен. Готовые конфиги лежат в `deploy/`.

### Развёртывание на nginx

Файлы: `deploy/nginx/tlkbars.ru.conf` (сайт + проксирование `/api/lead` и `/api/rates`), `deploy/nginx/snippets/tlkbars-security.conf` (заголовки безопасности), `deploy/systemd/bars-lead.service` (обработчик как служба). Инструкции по установке — в шапке каждого файла.

```bash
# 1. Код и зависимости
sudo git clone <repo> /var/www/tlkbars/repo && cd /var/www/tlkbars/repo
npm ci                       # devDependencies нужны: сборку делают 11ty/tailwind/esbuild

# 2. Секреты и адрес эндпоинта
sudo cp .env.example .env && sudo nano .env
#   BITRIX_WEBHOOK_URL=...   TELEGRAM_BOT_TOKEN=...   TELEGRAM_CHAT_ID=...
#   LEAD_API_URL=/api/lead   SITE_URL=https://tlkbars.ru
sudo chown www-data:www-data .env && sudo chmod 600 .env

# 3. Сборка статики
npm run build
```

### Если nginx уже настроен

Готовый конфиг из `deploy/` подключать не обязательно — достаточно, чтобы в вашем `server{}` было проксирование на обработчик:

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

И проверьте два места, где типовой конфиг статики конфликтует с этим проектом:

1. **Общий `location /assets/` с долгим кэшем ломает обновления форм.** `styles.css` и `main.js` собираются под постоянными именами, поэтому `expires 30d` + `immutable` означает, что вернувшийся посетитель до месяца будет работать со старым `main.js` — тем самым, который отправляет заявки, — и не увидит ни исправлений, ни смены адреса эндпоинта. Кэш нужно разделить:

   ```nginx
   location ~* ^/assets/(fonts|img)/ {
       add_header Cache-Control "public, max-age=2592000, immutable" always;
       access_log off;
   }
   location ~* ^/assets/(css|js)/ {
       add_header Cache-Control "public, max-age=3600, must-revalidate" always;
   }
   ```

2. **`try_files ... /404.html` отдаёт страницу 404 с кодом 200.** Поисковики считают такие «мягкие 404» обычными страницами и индексируют их. Правильнее:

   ```nginx
   location / {
       try_files $uri $uri/ $uri.html =404;
   }
   error_page 404 /404.html;
   ```

Помните про правило `add_header`: если в каком-то `location` он появился, заголовки уровня `server{}` в этом блоке перестают отдаваться — их нужно продублировать (например, через `include snippets/tlkbars-security.conf`).

**Важные детали:**

- **`LEAD_API_URL` читается на сборке, а не в рантайме** — адрес эндпоинта 11ty вшивает в HTML (`data-lead-endpoint`). Меняли `.env` → пересоберите `npm run build`, иначе браузер продолжит стучаться по старому адресу. Признак того, что сборка прошла без переменной: `grep -o 'data-lead-endpoint="[^"]*"' _site/index.html` показывает `http://localhost:3000/...` вместо `/api/lead`.
- **Node на сервере.** `ExecStart=/usr/bin/node server/index.ts` работает на Node ≥ 22.18 (исполняет TypeScript сам). На Node 20 (как в `.nvmrc`) в юните нужен вариант с `--import tsx` — он там закомментирован.
- **`X-Forwarded-For` обязателен** (в конфиге он есть): без него обработчик посчитает, что все заявки идут с одного IP — самого nginx, и антиспам заблокирует поток после `LEAD_RATE_LIMIT` заявок.
- **Обновление сайта:** `git pull && npm ci && npm run build && sudo systemctl restart bars-lead`. Перезапуск нужен только если менялся `server/` или `.env`.

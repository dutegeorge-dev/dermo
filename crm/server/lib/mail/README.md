# Рассылка — модуль «Ирбиса» (этап 1)

Автоотправка холодных писем продавцам из очереди лидогенерации (`lead_queue`, «Отобрать в работу» → раскладка по
дням) с отдельных **холодных доменов**: план дня, отправка в окне, повтор в той же цепочке, сбор ответов по IMAP,
автостатусы, стоп-лист. Раздел «Рассылка» (`/crm/mail`), право «Рассылка» (Пользователи → «Дополнительные права»);
ящики, домены и режим — только администратор.

**Жёсткое правило.** `tlkbars.ru`, его поддомены и ящики (`info@`, `sales@`) в рассылке не используются никогда.
Домен, ящик, подпись, шаблон, адрес посадочной страницы с `tlkbars.ru` не сохраняются; письмо, в котором он всё-таки
оказался, не отправляется (ошибка «Упоминание tlkbars.ru…»). Холодные домены вида `tlkbars-import.ru` — можно
(`mentionsMainDomain` в `shared/mail.ts`).

## Как это работает

1. **Явный запуск дня** (`runs.ts`, `planner.ts`) — сотрудник выбирает от 1 до 30 доступных ящиков и нажимает
   «Начать рассылку». Выбор сохраняется в `mail_runs` / `mail_run_mailboxes`; без такой записи воркер не строит план
   и ничего не отправляет. Повторный запуск в тот же день запрещён, «Допланировать новые касания» добавляет только
   новые строки очереди для тех же ящиков. По умолчанию `MAIL_FOLLOWUPS_ENABLED=false`: планируются только первые
   письма, весь дневной лимит идёт на новых получателей. При явном включении повторов они идут с ящика и на адрес
   первого письма, затем первые — по ящикам пропорционально остатку лимита.
   Письма ящика — равномерно по остатку окна (по умолчанию рабочие дни 09:30–17:30 МСК), случайный сдвиг ±40 %,
   не чаще раза в 4 минуты. Не влезшее — на следующий рабочий день. Письма рендерятся сразу и лежат в `mail_messages`
   целиком: тема, текст, ящик, шаблон и его версия, выбранные варианты, Message-ID.
2. **Отправка** (`sender.ts`, `agent.ts`) — локальный агент опрашивает CRM по HTTPS каждые 2 секунды и получает по
   одному письму на ящик с соблюдением расписания и минимального интервала. VDS не подключается к SMTP / IMAP.
   Сервер атомарно переводит `planned → sending` и проверяет стоп-лист (ИНН и адрес), статус продавца, лимит и
   `tlkbars.ru` непосредственно перед выдачей задания. Каждое письмо — одному получателю, только текст,
   `List-Unsubscribe` (mailto на тот же ящик). При включённых повторах сохраняется цепочка `Re:` /
   `In-Reply-To` / `References`. Зависшее `sending` автоматически не повторяется: SMTP мог уже принять письмо.
3. **Режимы** (Рассылка → «Режим и настройки», по умолчанию **dry-run**):
   - `dry_run` — письма рендерятся и пишутся в журнал, не отправляются;
   - `test` — все письма уходят на тестовый адрес, статусы продавцов и прогрев не меняются;
   - `live` — первое письмо продавцу → статус «Написал». Новый повтор создаётся только при
     `MAIL_FOLLOWUPS_ENABLED=true`. Миграция 0026 отменила старые запланированные повторы и деактивировала их
     шаблоны; история отправленных писем и воронки сохранена.
   «Пауза всей рассылки» останавливает отправку и план со всех ящиков сразу (снять — администратор).
4. **Входящие** (`inbound.ts`) — раз в 5 минут IMAP INBOX каждого ящика, новые письма с последнего UID (первый запуск
   только запоминает курсор). Письма в ящике не удаляются, не перемещаются, не отмечаются прочитанными.
   Сопоставление — `In-Reply-To` / `References` → отправленное; иначе адрес отправителя среди адресов этого ящика.
   - **возврат** (mailer-daemon / postmaster, `multipart/report; report-type=delivery-status`, 5xx): адрес продавца
     — невалидный, письма на него сняты; есть другой рабочий email — первое письмо уйдёт на него в следующем окне,
     иначе продавец — «Возврат»;
   - **автоответ** (`Auto-Submitted`, `X-Autoreply`, `Precedence: auto_reply`, «в отпуске», «автоматический ответ»)
     — ничего не меняет, повтор остаётся;
   - **ответ человека** — продавец «Ответил», запланированные письма и повтор сняты, текст ответа (без цитаты) —
     в истории продавца и во «Входящих». Подсказка «похоже на отказ» («нет», «не актуально», «не пишите»…). Человек
     ставит «Ответил +», «Ответил −» или «Отказ — в стоп-лист».
5. **Стоп-лист** (`do_not_contact`, ИНН и / или email): «Не писать», отказ из «Входящих», «Ответил −» с комментарием
   «не писать», вручную. Проверяется перед каждой отправкой, при плане, при отборе в работу и при сборе
   лидогенерации (продавец из стоп-листа сразу «Не писать»).
6. **Шаблоны** — только текст. Подстановки `{name_patronymic}` (имя и отчество руководителя из DaData; не удалось —
   «Добрый день!» без имени), `{brand}`, `{product}`, `{product_accusative}` (товар с «ваш / ваша / ваше / ваши» в
   винительном падеже), `{category}`, `{marking_note}`, `{link}`, `{signature}`, `{first_subject}`. Варианты
   `{фраза 1|фраза 2}` — выбираются по ИНН (то же письмо при повторном рендере).
   `{link}` = `https://<домен ящика>/wb/<страница категории>?l=<токен продавца>` (10 случайных символов,
   `lead_sellers.link_token`). Правка текста — новая версия шаблона. Несколько подходящих шаблонов — продавцы
   делятся между ними по ИНН (можно сравнивать). Предпросмотр и «Тест цепочки» (первое письмо + повтор сразу на
   тестовый адрес) — во вкладке «Шаблоны». Там же — страница категории, `{category}` и `{marking_note}`.
   Кнопка «Применить ИИ» (`POST /mail/templates/ai`) использует общий Claude через `claude-gateway.ru`: создаёт,
   улучшает или унифицирует **один шаблон**, а не делает платный запрос для каждого получателя. Результат — черновик
   полей темы и текста; проверка подстановок / основного домена и сохранение остаются обязательными. Без ключа ИИ
   кнопка скрыта, обычные шаблоны и рассылка работают.

## Автоматический прогрев

У нового ящика автоматически ставятся `status=warming`, `warmup_stage=1` и `warmup_stage_started_at=now()`. Ступени —
**5 → 10 → 15 → 20 → 25 писем в день**; календарное время само по себе лимит не увеличивает. Для перехода нужны пять
дней с фактическими live-отправками и не менее 25 live-писем на текущей ступени. `dry_run` и `test` не засчитываются.
Переход запрещён при SMTP-ошибках за последние три отправочных дня, hard bounce выше 3%, неактивном ящике / домене или
неуспешной проверке SMTP / IMAP. На пятой ступени ящик получает `active` и сохраняет лимит 25.

Обычный `daily_limit` может только уменьшить лимит ступени. `warmup_limit_override` задаётся отдельной кнопкой с причиной
и аудитом. Первые письма и повторы делят один лимит; перенесённые письма не создают долг на следующий день. При спаме /
rate limit — пауза 48 часов и возврат на ступень ниже с новым отсчётом. При auth / конфигурации — пауза до успешной
проверки. Hard bounce делает адрес невалидным; при доле выше 3% (от пяти отправок) новые первые касания останавливаются
до явной проверки базы администратором, повторы и IMAP продолжаются.

## Ящик на Яндекс 360

1. Купить холодный домен (не tlkbars.ru), подключить к Яндекс 360 для бизнеса, создать ящик (`ivan@<домен>`).
2. В ящике: Настройки → Почтовые программы — включить IMAP и «С сервера imap.yandex.ru по протоколу IMAP»;
   Яндекс ID → Безопасность → Пароли приложений → «Почта» — создать пароль приложения.
3. «Ирбис» → Рассылка → Ящики: «Добавить домен», затем «Ящик»: email, имя отправителя, SMTP `smtp.yandex.ru:465`
   (SSL), IMAP `imap.yandex.ru:993`, логины = email, пароль приложения и подпись. Первый автоматический лимит — 5.
   Хосты не зашиты — подходит любой провайдер с SMTP / IMAP.
4. Там же выпустить ключ локального агента. На Windows достаточно запустить **`crm/scripts/start-mail-agent.bat`**:
   при первом запуске он один раз спросит ключ и сохранит его в `%LOCALAPPDATA%\Irbis\mail-agent-token.txt`, дальше
   ничего вводить не нужно. BAT сам перезапускает агента после сбоя. Для автозагрузки один раз выполнить
   `powershell -ExecutionPolicy Bypass -File crm/scripts/install-mail-agent-startup.ps1`; ярлык `Irbis Mail Agent`
   появится в папке автозагрузки текущего пользователя и будет открывать агента свёрнутым. Ручной вариант без BAT:
   ```powershell
   $env:CRM_URL="https://datapoint-sync.ru"
   $env:CRM_MAIL_AGENT_TOKEN="<ключ из CRM>"
   npm run mail:agent
   ```
   Не закрывать окно во время рассылки. Агенту нужен исходящий HTTPS к CRM и доступ с этого ПК к портам Яндекса 465/993.
   В журнале у всех событий есть ISO-время; раз в минуту при простое выводится нормальное состояние и последний ответ CRM,
   успешные IMAP видны даже без новых писем, а после сбоя отдельно отмечается восстановление связи.
   Ключ показывается один раз; новый ключ отключает прежний. Без запущенного агента кнопка «Начать рассылку» неактивна.
5. Нажать «Проверить через агента» (SMTP- и IMAP-логин, необязательное тестовое письмо). Live станет доступен только
   после двух успешных проверок. При смене пароля или параметров подключения проверку нужно повторить.
6. Настройки → тестовый адрес (свой Gmail и Яндекс), режим `test`, «Тест цепочки» на любом продавце — оба письма ставятся
   агенту в очередь. Убедиться, что повтор пришёл в той же цепочке (Gmail и Яндекс Почта склеивают по `In-Reply-To` /
   `References` и теме `Re:`), затем отдельно подтвердить переход в `live`.

## DNS холодного домена

| Запись | Значение |
|---|---|
| MX | `mx.yandex.net.` (приоритет 10) — Яндекс 360 покажет при подключении |
| SPF (TXT `@`) | `v=spf1 redirect=_spf.yandex.net` — одна SPF-запись на домен |
| DKIM (TXT `mail._domainkey`) | ключ из Яндекс 360 → Почта → DKIM-подписи (селектор `mail`) |
| DMARC (TXT `_dmarc`) | `v=DMARC1; p=none; rua=mailto:<ящик для отчётов>` (через 2–4 недели — `p=quarantine`) |

Посадочные страницы — на том же холодном домене, `https://<домен>/wb/<страница категории>` (отдельная сборка сайта,
без ссылок на tlkbars.ru — не в «Ирбисе»). Проверка DNS и чёрных списков из «Ирбиса» — этап 2.

## Воркер на сервере (systemd)

```bash
sudo cp deploy/systemd/bars-crm-mail.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now bars-crm-mail
journalctl -u bars-crm-mail -f
```

Один экземпляр (advisory lock в PostgreSQL). `deploy-crm.sh` перезапускает службу, если она установлена. Вручную —
`cd crm && npm run mail:worker`; в разработке — `CRM_MAIL_INLINE=true` (воркер внутри `bars-crm`). Воркер только
планирует день; не останавливайте его при переносе SMTP / IMAP на рабочий ПК. Пароли, токены и тексты писем в лог не
пишутся.

## Переменные окружения

| Переменная | Зачем |
|---|---|
| `MAILBOX_SECRET_KEY` | на CRM: ключ AES-256-GCM для паролей ящиков: `openssl rand -hex 32`. Сменили — пароли ящиков ввести заново |
| `MAIL_FOLLOWUPS_ENABLED` | `false` по умолчанию: только первые письма, без ручных и автоматических повторов. `true` включает прежнюю цепочку через `followupDays` |
| `CRM_MAIL_INLINE` | на CRM: `true` — планировщик внутри bars-crm (разработка) |
| `CRM_URL` | на рабочем ПК: публичный HTTPS-адрес CRM, по умолчанию `https://datapoint-sync.ru` |
| `CRM_MAIL_AGENT_TOKEN` | на рабочем ПК: Bearer-ключ из «Рассылка → Ящики»; в CRM хранится только SHA-256 |
| `CRM_MAIL_AGENT_ONCE` | `1` или `--once`: один цикл опроса агента для диагностики |
| `CRM_MAIL_AGENT_INTERVAL_MS` | пауза агента при отсутствии заданий, по умолчанию 2000 мс |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `MAIL_DNS_RESOLVER`, `LEADCLICKS_SSH_KEY` | этапы 2–3 (уведомления, проверка DBL, логи переходов) |

## Таблицы и API

`mail_domains` (домен, адрес посадочных страниц, статус, селектор DKIM, результат проверки DNS), `mailboxes` (SMTP /
IMAP, пароль — `password_enc`, подпись, ручной предел, ступень и начало прогрева, причина удержания, остановка первых,
особый лимит, проверки и ошибки подключений, задания агенту, статус, причина и срок паузы, курсор IMAP), `mail_runs`
(один явный запуск на день), `mail_run_mailboxes` (до 30 выбранных ящиков), `mail_templates` (категория или «все» с
маркировкой / без, касание, тема, текст, версия), `mail_messages` (план, журнал и отправленные целиком: ящик, адрес,
шаблон и версия, варианты, Message-ID, In-Reply-To, статус planned / sending / sent / dry_run / failed / cancelled,
режим), `mail_inbound` (входящие: вид, сопоставление с письмом и продавцом, адрес возврата, текст, подсказка отказа,
решение человека), `do_not_contact`. В лидогенерации: `lead_sellers.link_token`, `lead_categories.slug / mail_name /
mail_note`, статус продавца «Ответил» (`replied`).

Агент: `POST /crm/api/mail/agent/next` и `/result` (только Bearer, без cookie / CSRF). Администратор выпускает ключ через
`POST /mail/agent/token`, задаёт особый лимит через `/mail/mailboxes/:id/limit-override` и подтверждает проверку базы через
`/mail/mailboxes/:id/review-bounces`.

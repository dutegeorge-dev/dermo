# Рассылка — модуль «Ирбиса» (этап 1)

Автоотправка холодных писем продавцам из очереди лидогенерации (`lead_queue`, «Отобрать в работу» → раскладка по
дням) с отдельных **холодных доменов**: план дня, отправка в окне, повтор в той же цепочке, сбор ответов по IMAP,
автостатусы, стоп-лист. Раздел «Рассылка» (`/crm/mail`), право «Рассылка» (Пользователи → «Дополнительные права»);
ящики, домены и режим — только администратор.

**Жёсткое правило.** `tlkbars.ru`, его поддомены и ящики (`info@`, `sales@`) в рассылке не используются никогда.
Домен, ящик, подпись, шаблон, адрес посадочной страницы с `tlkbars.ru` не сохраняются; письмо, в котором он всё-таки
оказался, не отправляется (ошибка «Упоминание tlkbars.ru…»). Холодные домены вида `tlkbars-import.ru` — можно
(`mentionsMainDomain` в `shared/mail.ts`).

## Как это работает

1. **План дня** (`planner.ts`) — воркер строит его в начале окна (по умолчанию рабочие дни 09:30–17:30 МСК), или
   кнопка «Построить план сейчас». Из `lead_queue` — всё на сегодня и просроченное: сначала повторы (только с ящика
   и на адрес первого письма), потом первые письма — по ящикам пропорционально остатку дневного лимита. Письма ящика
   — равномерно по остатку окна, случайный сдвиг ±40 % интервала, не чаще раза в 4 минуты. Не влезшее — на следующий
   рабочий день (видно в плане: «перенесено N на …»). Письма рендерятся сразу и лежат в `mail_messages` целиком:
   тема, текст, ящик, шаблон и его версия, выбранные варианты, Message-ID.
2. **Отправка** (`sender.ts`) — раз в 20 с по одному письму с каждого ящика (ящики независимы). Перед отправкой:
   стоп-лист (ИНН и адрес), статус продавца (ответил / возврат / «Не писать» — снять), `tlkbars.ru`. Каждое письмо —
   одному получателю, только текст, `List-Unsubscribe` (mailto на тот же ящик). Повтор — `Re: <тема первого>`,
   `In-Reply-To` и `References` = Message-ID первого (Message-ID генерируется на домене ящика).
3. **Режимы** (Рассылка → «Режим и настройки», по умолчанию **dry-run**):
   - `dry_run` — письма рендерятся и пишутся в журнал, не отправляются;
   - `test` — все письма уходят на тестовый адрес, статусы продавцов не меняются;
   - `live` — продавцам: первое письмо → «Написал» и повтор в очереди лидогенерации (через «Повтор через, дней»,
     на ближайший рабочий день — та же логика, что в «Сегодня»), повтор → «Повтор отправлен».
   «Пауза всей рассылки» останавливает отправку и план со всех ящиков сразу (снять — администратор).
4. **Входящие** (`inbound.ts`) — раз в 5 минут IMAP INBOX каждого ящика, новые письма с последнего UID (первый запуск
   только запоминает курсор). Письма в ящике не удаляются, не перемещаются, не отмечаются прочитанными.
   Сопоставление — `In-Reply-To` / `References` → отправленное; иначе адрес отправителя среди адресов этого ящика.
   - **возврат** (mailer-daemon / postmaster, `multipart/report; report-type=delivery-status`, 5xx): адрес продавца
     — невалидный, письма на него сняты; есть другой рабочий email — первое письмо уйдёт на него в следующем окне,
     иначе продавец — «Возврат»;
   - **автоответ** (`Auto-Submitted`, `X-Autoreply`, `Precedence: auto_reply`, «в отпуске», «автоматический ответ»)
     — ничего не меняет, повтор остаётся;
   - **ответ человека** — продавец «Ответил», запланированные письма и повтор сняты, текст ответа (без цитаты) —
     в истории продавца и во «Входящих». Подсказка «похоже на отказ» («нет», «не актуально», «не пишите»…). Человек
     ставит «Ответил +», «Ответил −» или «Отказ — в стоп-лист».
5. **Стоп-лист** (`do_not_contact`, ИНН и / или email): «Не писать», отказ из «Входящих», «Ответил −» с комментарием
   «не писать», вручную. Проверяется перед каждой отправкой, при плане, при отборе в работу и при сборе
   лидогенерации (продавец из стоп-листа сразу «Не писать»).
6. **Шаблоны** — только текст. Подстановки `{name_patronymic}` (имя и отчество руководителя из DaData; не удалось —
   «Добрый день!» без имени), `{brand}`, `{product}`, `{category}`, `{marking_note}`, `{link}`, `{signature}`,
   `{first_subject}`. Варианты `{фраза 1|фраза 2}` — выбираются по ИНН (то же письмо при повторном рендере).
   `{link}` = `https://<домен ящика>/wb/<страница категории>?l=<токен продавца>` (10 случайных символов,
   `lead_sellers.link_token`). Правка текста — новая версия шаблона. Несколько подходящих шаблонов — продавцы
   делятся между ними по ИНН (можно сравнивать). Предпросмотр и «Тест цепочки» (первое письмо + повтор сразу на
   тестовый адрес) — во вкладке «Шаблоны». Там же — страница категории, `{category}` и `{marking_note}`.

## Ящик на Яндекс 360

1. Купить холодный домен (не tlkbars.ru), подключить к Яндекс 360 для бизнеса, создать ящик (`ivan@<домен>`).
2. В ящике: Настройки → Почтовые программы — включить IMAP и «С сервера imap.yandex.ru по протоколу IMAP»;
   Яндекс ID → Безопасность → Пароли приложений → «Почта» — создать пароль приложения.
3. «Ирбис» → Рассылка → Ящики: «Добавить домен», затем «Ящик»: email, имя отправителя, SMTP `smtp.yandex.ru:465`
   (SSL), IMAP `imap.yandex.ru:993`, логины = email, пароль приложения, подпись, лимит (на старте 10–15).
   Хосты не зашиты — подходит любой провайдер с SMTP / IMAP.
4. «Проверить подключение» (SMTP- и IMAP-логин, тестовое письмо на указанный адрес).
5. Настройки → тестовый адрес (свой Gmail и Яндекс), режим `test`, «Тест цепочки» на любом продавце — убедиться, что
   повтор пришёл в той же цепочке (Gmail и Яндекс Почта склеивают по `In-Reply-To` / `References` и теме `Re:`).

## DNS холодного домена

| Запись | Значение |
|---|---|
| MX | `mx.yandex.net.` (приоритет 10) — Яндекс 360 покажет при подключении |
| SPF (TXT `@`) | `v=spf1 redirect=_spf.yandex.net` — одна SPF-запись на домен |
| DKIM (TXT `mail._domainkey`) | ключ из Яндекс 360 → Почта → DKIM-подписи (селектор `mail`) |
| DMARC (TXT `_dmarc`) | `v=DMARC1; p=none; rua=mailto:<ящик для отчётов>` (через 2–4 недели — `p=quarantine`) |

Посадочные страницы — на том же холодном домене, `https://<домен>/wb/<страница категории>` (отдельная сборка сайта,
без ссылок на tlkbars.ru — не в «Ирбисе»). Проверка DNS и чёрных списков из «Ирбиса» — этап 2.

## Воркер на сервере (systemd)

```bash
sudo cp deploy/systemd/bars-crm-mail.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now bars-crm-mail
journalctl -u bars-crm-mail -f
```

Один экземпляр (advisory lock в PostgreSQL). `deploy-crm.sh` перезапускает службу, если она установлена. Вручную —
`cd crm && npm run mail:worker`; в разработке — `CRM_MAIL_INLINE=true` (воркер внутри `bars-crm`). В логе — ящик,
адрес получателя, статус; паролей, токенов и текстов писем там нет (тексты — только в БД).

## Переменные окружения

| Переменная | Зачем |
|---|---|
| `MAILBOX_SECRET_KEY` | ключ AES-256-GCM для паролей ящиков: `openssl rand -hex 32`. Сменили — пароли ящиков ввести заново |
| `CRM_MAIL_INLINE` | `true` — воркер рассылки внутри bars-crm (разработка) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `MAIL_DNS_RESOLVER`, `LEADCLICKS_SSH_KEY` | этапы 2–3 (уведомления, проверка DBL, логи переходов) |

## Таблицы

`mail_domains` (домен, адрес посадочных страниц, статус, селектор DKIM, результат проверки DNS), `mailboxes` (SMTP /
IMAP, пароль — `password_enc`, подпись, лимит, начало прогрева, статус warming / active / paused / burned, причина
и срок паузы, курсор IMAP), `mail_templates` (категория или «все» с маркировкой / без, касание, тема, текст, версия),
`mail_messages` (план, журнал и отправленные целиком: ящик, адрес, шаблон и версия, варианты, Message-ID,
In-Reply-To, статус planned / sending / sent / dry_run / failed / cancelled, режим), `mail_inbound` (входящие: вид,
сопоставление с письмом и продавцом, адрес возврата, текст, подсказка отказа, решение человека), `do_not_contact`.
В лидогенерации: `lead_sellers.link_token`, `lead_categories.slug / mail_name / mail_note`, статус продавца
«Ответил» (`replied`).

## Этапы 2–3 (не сделано)

Этап 2: несколько доменов и ящиков с прогревом (график 10 → 20 → целевой лимит, `warmup_start` уже есть), здоровье
ящиков и автопауза по возвратам, домен на паузу, DNS / DBL / SURBL, «Мощность», «Итоги» по ящикам / шаблонам /
вариантам. Сейчас из защиты есть: SMTP-отказ с признаками спама / лимита (`5.7.1`, `554`, «spam», «limit») → ящик на
паузу на 48 часов. Этап 3: переходы по ссылкам (логи Nginx холодных доменов), единая лента входящих с ответом из
«Ирбиса», уведомления в Telegram.

# Лидогенерация WB — модуль «Ирбиса»

Работает в два шага (решение владельца, ноябрь 2026: «по максимуму оставить все контакты, фильтровать потом сам»):

1. **«Собрать базу на месяц»** — продавцы Wildberries из выдачи по запросам категорий; по каждому сервер бесплатно
   добирает профиль WB (ИНН, юрназвание, email из профиля), отзывы о продавце и реквизиты DaData (статус, дата
   регистрации, руководитель, ОКВЭД, регион) — и кладёт **всех с российским ИНН в «Базу» без отсева**.
2. **«Отобрать в работу»** (вкладка «База») — по фильтру «Базы» (отзывы, возраст, регион, ООО / ИП, действующие…)
   случайно N продавцов на категорию; по каждому — **полные** телефоны и email из Checko (платно — поэтому только здесь)
   и с сайта. Взятые раскладываются по рабочим дням: каждый день во вкладке «Сегодня» — 30 продавцов (категории
   вперемешку), им пишут вручную. Нет ответа через 4 дня после письма — продавец снова в «Сегодня» как повтор.

Раздел: меню «Лидогенерация» (`/crm/leadgen`). Доступ — администратор или сотрудник с правом «Лидогенерация WB»
(Пользователи → сотрудник → «Дополнительные права»).

## Сбор через расширение в браузере (основной режим)

**Почему.** С ноября 2026 поиск и каталог продавцов WB серверам не отвечают: 403 и антибот «Подозрительная активность»
и с европейского, и с российского сервера (проверено). Браузер под управлением Playwright / Puppeteer WB тоже
распознаёт. Пропускает WB обычный браузер человека, поэтому выдачу берёт **расширение Chrome «Ирбис · сборщик WB»**
(`crm/tools/wb-extension`) в браузере сотрудника. Расширение ничего не маскирует и не обходит и в работу сайта не
вмешивается: открывает страницы WB в отдельном окне в спокойном темпе (пауза 6–15 с), прокручивает выдачу и читает со
страницы артикулы товаров (ссылки `/catalog/<артикул>/detail.aspx`), на странице продавца — ещё «N товаров».
Продавца по артикулу «Ирбис» узнаёт из карточки товара (статика WB отдаётся серверу). Если WB показал проверку —
расширение останавливается. С версии 1.1 расширение не встраивает в страницу скриптов (1.0 копировала её сетевые
ответы) — меньше зависимости от того, как устроен сайт WB.

**Выдача WB не листается по `?page=N`** (страницы 2 и 3 показывают те же товары — проверил владелец), товары только
подгружаются при прокрутке. Поэтому на каждый поисковый запрос — одна страница, расширение прокручивает её до
«Товаров на запрос (браузер)» (по умолчанию 300) или до конца выдачи (не дольше 3 минут).

**Как это идёт.** «Собрать базу на месяц» → «Расширение в браузере» (по умолчанию). Задача получает статус
`collecting` («Ждёт сборщик в браузере»): расширение спрашивает `GET /leadgen/collector/next` → страница выдачи по
запросу категории → прокручивает → присылает артикулы `POST /leadgen/collector/result`. Выдача собрана — задача
возвращается воркеру (этап `enrich`), дальше браузер не нужен. Страницы продавцов не открываются (SKU не собираем —
решение владельца: размер продавца видно по отзывам).

Окно WB можно отодвинуть, но не сворачивать: в свёрнутом / фоновом окне WB не дорисовывает выдачу. API принимает и
JSON ответа WB (`data`) — на случай, если понадобится снова.

**Установка (один раз, Chrome или Edge):**
1. «Ирбис» → Лидогенерация → Сбор → «Сборщик в браузере» → «Скачать расширение», распаковать архив;
2. `chrome://extensions` (Edge — `edge://extensions`) → «Режим разработчика» → «Загрузить распакованное расширение»
   → папка `irbis-wb-extension`;
3. там же в «Ирбисе» — «Выпустить ключ» (показывается один раз; новый ключ отключает старый);
4. значок расширения → адрес «Ирбиса» (`https://datapoint-sync.ru/crm`) и ключ → «Запустить».

Браузер должен быть открыт, пока идёт сбор (компьютер не спит); вкладку WB можно не трогать. Остановить — «Остановить»
в расширении; продолжит с того же места. Ключ проверяется по SHA-256, маршруты сборщика — без сессии, по
`Authorization: Bearer`.

**Время.** Выдача: ~45 запросов × (1–2 мин прокрутки + пауза) ≈ 1–1,5 ч. Реквизиты на сервере (WB + DaData, без
браузера): ~1–1,5 с на продавца, 3 000 продавцов ≈ 1 ч.

## Вкладки

| Вкладка | Что там |
|---|---|
| Сегодня | первые письма по плану на день (не больше «продавцов в день») и повторы; у каждого — все телефоны и email с источником, бренд, 2–3 товара со ссылками, готовая первая строка письма (правится, копируется), кнопки статуса |
| База | **все** собранные продавцы: фильтры — категория, месяц сбора, в работе / в базе, статус, контакты Checko (найдены / нет / не запрашивали), телефон, email, отзывы от–до, возраст компании, регион, ООО / ИП, действующие; «Фильтр по умолчанию» (из настроек); **«Отобрать в работу»** по текущему фильтру; экспорт XLSX (листы «Продавцы» и «Контакты») и CSV (`;`, UTF-8 с BOM) |
| Категории | название, поисковые запросы, стоп-слова, «Честный знак» и пометка, шаблон первой строки (`{brand}`, `{product}`), активна |
| Сбор | готовность (воркер, ключи, сборщик в браузере), прогресс задач (сбор в базу / отбор в работу) по категориям, «Остановить» / «Продолжить» / «Завершить досрочно», журнал ошибок, настройки |
| Итоги | по категориям, по взятым в работу: отправлено, возвраты, ответы, положительные, % от отправленных |

## Задачи (`job.ts`)

**Сбор в базу** (`params.kind = collect`), этапы:

1. **collect** — выдача WB по запросам категорий (из браузера — см. выше; с сервера — страницы 1…`searchPages`, курсор
   `checkpoint.collect[категория] = {q, page}`). Товары со стоп-словами в названии отбрасываются, остальные
   группируются по продавцу (`lead_candidates`).
2. **enrich** — по каждому кандидату: профиль WB (`supplier-by-id`) → нет российского ИНН (10 / 12 цифр с верной
   контрольной суммой) — не в базу (`no_inn`); ИНН уже в базе (другая категория, второй кабинет, прошлые сборы) —
   склейка в одну запись (`merged`: ID кабинетов, бренды; при новом сборе обновляются отзывы); иначе отзывы о продавце
   (`suppliers-shipment`) + DaData `findById/party` → `lead_sellers` **без отсева** (ликвидируемые и молодые тоже — их
   отсекает фильтр «Базы»), email / телефон из профиля WB — в `lead_contacts` (источник `wb`, email с проверкой MX),
   3 товара для письма и первая строка по шаблону категории. Checko здесь не вызывается.

**Отбор в работу** (`params.kind = pick`, `POST /leadgen/pick {filter, perCategory}`), этапы:

1. **pick** — по каждой категории: продавцы базы по фильтру, ещё не в работе, не «Не писать», без пометки «нет
   контактов» — в случайном порядке (`md5(ИНН || id задачи)`, воспроизводимо после остановки), пока не наберётся N.
   По каждому — Checko (организация — `/v2/company`, ИП — `/v2/entrepreneur`: все телефоны, email, сайт), если email
   нет — сайт (главная + «Контакты»). Телефоны → `+7XXXXXXXXXX` (маскированные отбрасываются), email → нижний регистр,
   синтаксис + MX домена (невалидные хранятся с пометкой). Есть телефон или рабочий email → в работу (`picked_at`);
   нет → `contacts_status = none`, в следующие отборы не попадает, берётся следующий.
2. **schedule** — взятые этим отбором по рабочим дням после уже запланированных первых писем (не раньше сегодня),
   `perDay` (30) в день, категории по кругу (6 категорий → по 5 из каждой) → `lead_queue`.

**Остановка и продолжение.** «Остановить» — задача доделывает текущий шаг и встаёт на паузу. «Продолжить» —
с курсора выдачи и статусов кандидатов: уже пройденные страницы и проверенные продавцы повторно не запрашиваются.
Временные сбои (сеть, 429 / 5xx — с повторами 2, 4, 8… с; лимит DaData; баланс Checko) переводят задачу в «Ошибка»,
и воркер сам продолжает её через 15 мин (DaData — через 6 ч), до 6 раз подряд. Упал воркер / перезагрузили сервер —
задачу без отметки «жив» дольше 2 мин подхватывает следующий запуск.

## Переменные окружения (`crm/.env`)

| Переменная | Зачем |
|---|---|
| `DADATA_TOKEN` | токен DaData (API-ключ из личного кабинета). Без него сбор не запускается |
| `CHECKO_API_KEY` | ключ Checko (параметр `key`). Пусто — контакты только с WB |
| `WB_PROXY` | `http://user:pass@host:port` — прокси для запросов к WB с сервера (статика WB отвечает и из Европы — обычно не нужен) |
| `LEADGEN_WB_CONFIG` | путь к своему файлу эндпоинтов WB поверх `wb-endpoints.json` (правка без git) |
| `CRM_LEADGEN_INLINE` | `true` — воркер внутри `bars-crm` (разработка) |

Ключи в git не попадают, в логах и журнале ошибок ключи в адресах заменяются на `***`.

## Воркер на сервере (systemd)

```bash
sudo cp deploy/systemd/bars-crm-leadgen.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now bars-crm-leadgen
journalctl -u bars-crm-leadgen -f
```

Одновременно работает один воркер (advisory lock в PostgreSQL). `deploy/deploy-crm.sh` перезапускает службу, если
она установлена. Вручную: `cd crm && npm run leadgen:worker`. На вкладке «Сбор» видно, жив ли воркер.

## Эндпоинты WB и как их чинить

Все адреса — в `wb-endpoints.json` (плейсхолдеры `{query} {page} {dest} {supplierId} {nm} {vol} {part} {basket}`).
У поиска, каталога продавца и профиля можно указать несколько `urls` — пробуются по очереди, рабочий запоминается.

| Ключ | Что | Проверено |
|---|---|---|
| `sellerInfo` | `static-basket-01.wbbasket.ru/vol0/data/supplier-by-id/{id}.json` — юрназвание, ИНН, ОГРН, торговая марка, иногда email | живым запросом, ноябрь 2026 |
| `sellerRating` | `suppliers-shipment-2.wildberries.ru/api/v1/suppliers/{id}` + заголовок `x-client-name: site` — `feedbacksCount` | живым запросом, ноябрь 2026 |
| `upstreams` | `cdn.wbbasket.ru/api/v3/upstreams` → `origin.mediabasket_route_map` — какая корзина (`basket-NN`) хранит карточку | живым запросом, ноябрь 2026 |
| `card` | `{basket}/vol{vol}/part{part}/{nm}/info/ru/card.json`, опция «Страна производства» | живым запросом, ноябрь 2026 |
| `search` | `u-search.wb.ru/exactmatch/ru/common/v18/search`, запасной — `search.wb.ru/…/v14/search` | серверам — 403 (и из Европы, и из России, ноябрь 2026); используется только в режиме «С сервера» |
| `sellerCatalog` | `u-catalog.wb.ru/sellers/v4/catalog?supplier=…`, запасной — `catalog.wb.ru/…` | то же; в режиме браузера каталог присылает расширение |

Ответы разбираются терпимо: товары — `products` или `data.products`, отзывы — `feedbacks` / `nmFeedbacks`, всего —
`total` / `data.total` (нет `total` — SKU считаются страницами; нет рейтинга — отзывы суммируются по каталогу).

**Сломалось (в журнале «Сбор» — 403 / 404 / «ни один адрес … не ответил»):**

1. На сервере: `cd /var/www/tlkbars/repo/crm && npm run leadgen:check` — что отвечает, что нет
   (`-- --query "гантели" --registry` — заодно DaData и Checko по ИНН найденного продавца).
2. Найти новые адреса: `scripts/wb-probe.cjs` (Playwright, инструкция в начале файла) открывает wildberries.ru,
   делает поиск, открывает карточку и продавца и печатает XHR-запросы к API WB с ключами ответа. Либо вручную:
   DevTools → Network → Fetch/XHR на сайте.
3. Поправить `wb-endpoints.json` (через PR) или положить свой файл и указать `LEADGEN_WB_CONFIG=/etc/bars-crm/wb-endpoints.json`
   (в нём достаточно изменённых ключей), затем `sudo systemctl restart bars-crm-leadgen`, `npm run leadgen:check`,
   и на вкладке «Сбор» — «Продолжить».
4. 403 на всё и антибот — не российский IP: задать `WB_PROXY`.

**Checko.** Контакты — `data.Контакты`: `Тел` (массив), `Емэйл` (массив), `ВебСайт` (строка), `Телеграм` (не берём) —
сверено с живым ответом `/v2/company` (ноябрь 2026). Если Checko переименует поля, код ищет их по смыслу названия
(«телефон/phone», «емэйл/email/почт», «сайт/web»). `meta` — `status`, `today_request_count`, `balance`.

## Настройки (вкладка «Сбор» → «Пороги фильтров и настройки», `settings.leadgen`)

| Настройка | По умолчанию |
|---|---|
| Товаров на запрос (браузер) / пауза браузера | 300 / 6–15 с |
| Страниц выдачи на запрос (сбор с сервера) | 20 |
| Отбор по умолчанию: отзывов / возраст компании / продавцов на категорию | 1 000…50 000 / от 12 мес. / 300 — подставляются кнопкой «Фильтр по умолчанию» в «Базе» и в окно отбора |
| Продавцов в день, рабочие дни, праздники | 30, пн–пт, — |
| Повтор через | 4 дня (на ближайший рабочий) |
| Пауза WB / случайная добавка / DaData и Checko | 400 / 400 / 150 мс |

Фильтров «по умолчанию» при сборе нет — сбор кладёт в базу всех. Отбор фильтрует по тому, что выбрано в «Базе».
Число SKU и «Страна производства» не собираются (решения владельца: SKU — только через браузер, долго; страна — «в
поддельных декларациях пишут Россия», не показатель).

## Таблицы

`lead_categories` (поле `quota` больше не используется), `lead_jobs` (вид collect / pick, месяц, статус, этап,
прогресс, чекпоинт, фильтр отбора, журнал ошибок), `lead_candidates` (кандидаты сбора: товары из выдачи, статус
new / in_base / merged / no_inn / error + причина), `lead_sellers` (ИНН — ключ; вся база: `picked_at` / `pick_job_id`
— в работе, `contacts_status` found / none / null + `contacts_job_id` — контакты Checko запрашивались),
`lead_contacts` (тип, значение, источник wb / checko / site, валиден, дата), `lead_queue` (план касаний first /
followup), `lead_events` (история статусов). Право — `users.permissions` (`leadgen`).

## Заложено на потом (не сделано)

- Автоотправка писем через SMTP с троттлингом и разбор входящих по IMAP: статусы уже событиями (`lead_events`),
  очередь касаний (`lead_queue`) — отправщику достаточно брать `planned` на день и ставить статусы тем же
  `setSellerStatus`.
- Учёт кликов по посадочным страницам категорий (`?l=<ИНН или id>`): событие `click` в `lead_events`.
- Продавцы Ozon: второй источник рядом с `wb.ts` (интерфейс `LeadSources` в `job.ts`), поле площадки у кандидата.

## 1. Что это за бизнес и зачем система

**ООО ТЛК БАРС** — закупка и доставка товаров из Китая «под ключ» (ВЭД):
находят поставщика, закупают, везут (ж/д, море, авто, авиа), растаможивают,
довозят клиенту. Офис-команда в Гуанчжоу, юрлицо в Московской обл. (Красногорск).
Типичные грузы: искусственная трава, LVT/линолеум, плинтус, LED-светильники.
Одновременно в работе ~10 контейнеров — главная боль владельца: «что на этой
неделе, на следующей, через месяц — ничего не понимаю». Отсюда календарь и
понятный «ход сделки».

Сайт `tlkbars.ru` — публичный (11ty, заявки → Bitrix24 + Telegram). Внутренний
раздел `https://tlkbars.ru/crm/` — закрытый, по логину/паролю, для команды:

1. **База знаний** (как Confluence): пространства, дерево страниц, история версий.
2. **Справочник для звонков** — скрипт ответов менеджера (перенесён 1:1 из
   `crm/seed/kb-call-script.json`, хранится в БД, есть история и откат).
3. **CRM**:
   - **Воронка продаж** — лиды, только работа с клиентом до депозита;
   - **Сделки** — реальные заказы/отгрузки: груз, документы, деньги, даты, календарь;
   - **Клиенты / Поставщики / Подрядчики** — контрагенты с реквизитами;
   - **Документы** — реестр всех документов;
   - **Товары** — справочник с ценами.

## 2. Глоссарий (слова владельца)

| Термин | Что значит |
|---|---|
| **Лид** | запись в воронке продаж (`deals`, ключ `BARS-12`) — переговоры до депозита |
| **Сделка** | реальный заказ = одна отгрузка (`shipments`), называется по грузу: «Линолеум коричневый». Номер «№ 12» вторичен |
| **Схема** | `commission` комиссия (основная: закупаем от своего имени за счёт клиента), `supply` поставка (покупаем и продаём), `teu` ТЭУ (клиент покупает сам, мы везём и растаможиваем) |
| **Поручение** | «Поручение на закупку» — приложение к договору комиссии; генерируется из инвойса поставщика, DOCX по шаблону владельца. Одна сделка — одно поручение. Выпускается **после инвойса, но до оплаты депозита** клиентом |
| **Партийный номер** | в поручении просто 1, 2, 3 по порядку позиций |
| **Депозит / остаток** | клиент платит депозит → производство; остаток поставщику платят перед погрузкой |
| **Фрахт** | оплата перевозки |
| **Инвойс перевозчика** | счёт перевозчика (контрагент-подрядчик), привязывается к сделке |
| **СМГС** | ж/д накладная; CMR — авто; коносамент — море |
| **ДТ (ГТД)** | декларация на товары — даёт сумму таможенных платежей |
| **Декларация соответствия / сертификат** | `conformity`; привязывается к **товарам** (позициям), видна во всех сделках с этим товаром |
| **СВХ** | склад временного хранения (подрядчик) |
| **ТН ВЭД** | код товара (`hs_code`) |
| **«Честный знак»** | маркировка: не требуется / нужна / нанесена |
| **Номер груза** | у владельца = номер контейнера (отдельного поля нет) |

## 3. Бизнес-процесс в системе

```
Лид (воронка, только переговоры, КП файлами)
  └─ «Создать сделку» (клиент и лид подставятся)      ← повторный заказ — сразу сделкой, без воронки
Сделка, 8 этапов (этап = следствие фактических дат, руками не выбирается):
  1 Заказ сформирован     ждём: оплата депозита  │ сделать: инвойс поставщика → поручение (кнопкой) → подписанное поручение
  2 Производство          ждём: товар готов
  3 Готов к отгрузке      ждём: погрузка          │ сделать: остаток поставщику, фрахт, номер контейнера (без него погрузку не отметить)
  4 Погружен              ждём: отправка поезда/судна
  5 В пути                ждём: прибытие на таможню (+ необязательные отметки: граница, перегруз)
  6 На таможне            ждём: выпуск            │ сделать: таможенные платежи, документы
  7 Выпущен               ждём: доставка клиенту
  8 Доставлен             → закрыть сделку вручную («Закрыть сделку»)
```

Документная цепочка (комиссия): договор комиссии с клиентом (рамочный) →
контракт с поставщиком → **инвойс поставщика** (позиции → справочник товаров;
можно сразу «Новая сделка») → **поручение** № N к договору комиссии (номер —
следующий по договору) → подписанный скан → счета подрядчиков (перевозчик,
брокер, СВХ) → СМГС/CMR → ДТ → сертификаты → счёт клиенту.

**План / факт**: смета поручения (статьи `COST_CATEGORIES`) против факта —
инвойсы поставщика (товар), счета подрядчиков (статья по виду подрядчика),
ДТ (таможня). Факт > плана подсвечивается — по п. 3.4 договора комиссии разницу
доплачивает клиент.

## 4. Решения владельца и почему (не переигрывать без него)

Хронология ключевых решений — чтобы не предлагать уже отвергнутое:

1. **Воронка ≠ сделки.** Сначала всё было в «сделке воронки», владелец сказал:
   в воронке «слишком много информации», в сделке «очень мало». Итог (миграция
   0005): воронка — только работа с клиентом (клиент, контакт, «что хочет»,
   описание, исполнитель, срок, приоритет, метки, КП — файлами-вложениями);
   **всё остальное — в сделке**: схема, поставщик, договоры, ТН ВЭД, вес/объём,
   маршрут, разрешения, все документы, поручение, план/факт, подрядчики.
2. **Воронку владелец будет менять сам** («не трогай»). Этапы воронки
   редактируются в UI (admin). Без просьбы воронку не перестраивать.
3. **Три слоя (лид → заказ → отгрузка) отвергнуто** как «лютое усложнение».
   Две сущности: воронка и сделки. Одна сделка = одна отгрузка (контейнер).
   Сборных грузов (несколько клиентов в контейнере) нет.
4. **Этапы — по таблице владельца**, «делай попроще»: ключевая дата (план/факт)
   на этап + флажки ожиданий. Потом добавлен этап 1 «Заказ сформирован»
   (поручение до депозита) — миграция 0006 сдвинула этапы.
5. **Закрытие сделки — вручную.** Нумерация — своя, но **называем по грузу**
   («С-001 нихера не дают»). Номер «№ 12» только для ссылок.
6. **Номер контейнера обязателен** — но к моменту погрузки (на депозите его ещё нет).
7. **Трекинга от перевозчиков нет.** Трекинг для клиента — «в будущем, не сейчас».
8. **Календарь — главный инструмент.** Был отдельной страницей, владелец
   попросил сделать третьим видом в «Сделках» (доска / список / календарь).
   В клетке месяца крупно **действие** («₽ Оплатить остаток»), под ним груз —
   «приходится наводиться мышкой» было плохо.
9. **Карточка сделки — «всё сразу»**: деньги, товары с ТН ВЭД и ценами,
   сертификаты на товары, документы, ход сделки, все поля. «Ход сделки» —
   этапы простыми словами (что происходит, что сделать, чего ждём, что дальше),
   а не таблица дат («нихера не понятно»).
   Порядок блоков (октябрь 2026, по просьбе владельца): ход сделки → документы → деньги → товары → история →
   «Расчёт для клиента» (КП и поручение) и «Спецификация для перевозчика» — в самом низу, свёрнуты. В «Ходе сделки»:
   этап 1 — поручение, этапы 4–5 — упаковочный лист и спецификация, этап 6 — пакет документов для таможни.
10. **Без 1С.** Цены видят все сотрудники. Валюты: CNY, USD, EUR, RUB.
11. **ИИ подключён (октябрь 2026)**: задумка владельца — «я только подгружаю документы, ИИ сам парсит:
    кто, что, сколько, контейнер, какая сделка». Форматы инвойсов у поставщиков и перевозчиков разные,
    поэтому — модель, а не шаблоны. Принцип сохранён: ИИ заполняет черновик формы, **сохраняет человек**.
    Плюс чат «Спросить ИИ» — запросы простыми словами, **только чтение** (менять данные через чат пока
    нельзя — следующий шаг, если попросит). Доступ — через шлюз владельца (`claude-gateway.ru`), данные
    документов уходят наружу — это решение владельца. **Лимит шлюза — 100 млн единиц в месяц**, нужно ≥1000 документов:
    первая версия (Opus, файл и справочник CRM целиком в запросе) тратила 150–650 тыс. на документ — владелец
    сказал «очень дорого». Теперь: модель Haiku 5.5, текст из файла достаёт код, сопоставление со справочником и
    сделками — код; 2–4 тыс. на документ, 4–6 тыс. на вопрос в чате. Не возвращать дорогую схему без согласия.
12. **Расчёт для клиента (октябрь 2026).** Очерёдность владельца: инвойс поставщика → сделка → он сам вписывает
    стоимость перевозки (инвойса перевозчика ещё нет) → считается пошлина → КП и поручение из **одной формы**.
    Посчитанные пошлины **хранятся в сделке** и пересчитываются перед таможней по новому курсу. Таможенная стоимость =
    товар + ½ доставки; НДС 22 % (10 % — галочкой у товара); брокер — 20 000 ₽ по умолчанию; сбор за таможенные
    операции не считаем. Вес и объём — обязательны при создании сделки. Ставки — из справочника ТН ВЭД (выгрузка
    tws.by), а не «ИИ гуглит пошлину» (дорого и ненадёжно). Шаблон КП — из docx владельца (`templates/kp.docx`).
13. **После погрузки / на таможне (октябрь 2026).** Перевозчик просит спецификацию («счёт-фактура — упаковочный
    лист — спецификация»), шаблоны у перевозчиков немного разные → наш шаблон + «заполнить шаблон перевозчика» (ИИ
    только размечает ячейки, значения пишет код). Упаковочный лист добавляется в сделку после погрузки. На таможне —
    одна кнопка «Сформировать документы для таможни»: ZIP с инвойсами за товар и перевозку, их оплатами (платёжки
    прикрепляются к инвойсу, а не отдельными документами), упаковочными листами, спецификацией, сертификатами на товары.
    Спецификация — **ровно по позициям инвойса / упаковочного листа**, а не по кодам ТН ВЭД (владелец: «всё должно
    совпадать по позициям, чаще деление по местам: рулоны 2 м — 65 шт., 3 м — 105 шт.»).
    **Оплаты:** галочки «остаток поставщику / фрахт / таможенные платежи» и статус оплаты инвойсов / счетов / ДТ — одно
    и то же («галочка стоит, а инвойс не оплачен» — была жалоба), держатся согласованными (`lib/payments.ts`). Каждый
    факт оплаты **по желанию** подтверждается платёжкой (MT103 / «Заявление на перевод») — не обязательно. В блоке
    «Документы» одна кнопка «Загрузить документ» — тип определяет ИИ (было много «+»: «упростить UI»).
15. **База фабрик (октябрь 2026).** У владельца и сотрудников в WeChat тысячи контактов заводов без порядка —
    искать невозможно. Фабрика-кандидат — **отдельная таблица `factories`**, не контрагент: договора нет, имени
    и названия компании часто нет (только имя в WeChat вроде «A-某某地板厂-小王»). Решения владельца:
    **кандидатов видит только админ и тот, кто нашёл**; фабрики-поставщики (после «Сделать поставщиком») — все.
    Работник-поисковик заводит фабрику с телефона: скриншоты профиля и переписки WeChat, фото, прайсы → ИИ
    (Haiku, ~5 тыс. токенов) заполняет анкету владельца (10 вопросов: место и сроки производства, цены с
    характеристиками, вес/объём партии, минимальный объём, экспортная лицензия, ВТБ Шанхай, работали ли с РФ,
    образцы, код ТН ВЭД) и цены, работник проверяет. Дубли — по WeChat ID / телефону / имени; про чужого
    кандидата сообщаем только, кто его нашёл. Цены фабрик (`product_offers`) привязаны к товарам справочника:
    размер рулона и цвет — вариант, а не новый товар.
16. **Товары и расчёт цены для клиента (октябрь 2026).** Товары раньше заводились «втупую» из каждой строки инвойса
    («трава 20 мм 1×25 м», «… 2×25 м» — разные товары) — владелец: из-за цвета или размера рулона это не новый
    товар. Теперь товар = название без варианта (`productBaseName`: без «N×M м», цветов, скобок), варианты — названия
    позиций и цен фабрик; старые дубли объединяются кнопкой на странице «Товары» (предложение по группам, владелец
    подтверждает). Толщина ворса («20 мм» / «35 мм») — разные товары. В карточке товара — «Рассчитать для клиента»:
    цена фабрики × объём + доставка + 4 % за перевод + пошлина/НДС по коду товара + брокер 20 000 + СВХ / до склада
    + **маржа суммой на партию** (решение владельца) → цена за единицу в рублях и КП в Word (`templates/product_kp.docx`
    — из КП владельца). Доставка — **ставки перевозчиков в справочнике** «Ставки доставки» (за контейнер или сборный
    груз за м³ с «1 м³ = N кг» и сбором за отправку; вставить переписку — ИИ разберёт) **или вручную** — владелец
    просил оба варианта. Реальные ставки перевозчиков в git не кладём — их заносят в CRM.
17. **Клиент ↔ договор комиссии (октябрь 2026).** Загрузили договор — ИИ берёт полные реквизиты клиента (банк,
    ОГРН, КПП, подписант, ИП/ООО — `server/lib/requisites.ts`): новый клиент создаётся с ними, найденному дописываются
    пустые поля. В карточке клиента — «Договор комиссии»: DOCX по шаблону владельца (`templates/commission_contract.docx`
    — из его договора, поля клиента, номер, дата, срок), номер — следующий по порядку, документ-черновик с файлом.
    Преамбула склоняется кодом («в лице генерального директора Ивановой И.И., действующей…», ИП — «Индивидуальный
    предприниматель …, именуемая…»). В форме нового контрагента — «Вставить реквизиты» (любой текст → ИИ раскладывает
    по полям, ~2 тыс. токенов). **Сканы PDF без текста ИИ не разбирает** (решение владельца «пока без сканов»):
    модель не вызывается, форма просит заполнить вручную.
    На этапе «Готов к отгрузке» в чек-листе — «Загрузить инвойс перевозчика» перед «Оплатить фрахт» (к нему
    прикрепляется платёжка за фрахт; владелец: «на этом этапе — инвойс и платёжка перевозчика»).
    На этапе «На таможне» — «Загрузить СМГС (ж/д накладную)» перед «Документы для таможни поданы»; нет транспортной
    накладной — пакет для таможни пишет об этом в «чего не хватает».
18. **Чистка карточки сделки (октябрь 2026, владелец: «всё смешано… убери дубли»).** Справа — «Участники сделки»
    (клиент с контактом, поставщик, перевозчик, прочие подрядчики строками; перевозчик не дублируется) и «Сделка»
    (менеджер, схема, контейнер, вес, объём, лид, заметки). Убраны с карточки: код ТН ВЭД сделки (коды — у товаров),
    «Разрешения и маркировка», выбор инвойса перевозчика (подбирается сам, виден в «Ходе сделки» и документах);
    маршрут (тип доставки, откуда, куда) — в «Расчёте для клиента», он нужен только для КП. Договор с клиентом и
    контракт поставщика — наверху блока «Документы». «Сформировать поручение» — только в расчёте и в чек-листе этапа 1.
    В «Деньгах» — итоги в $ и ₽ по курсу ЦБ: доставка, товар с доставкой, всё вместе (факт, где нет — план).
    Расчёт цены товара: вес и объём **всей партии** задаёт пользователь («объём одного м²» — бессмыслица).
    Инвойс известного поставщика: позиция без совпадения по названию ищет его товар по артикулу (`articleCodes`,
    «M103-4») — названия у поставщиков то по-английски, то по-русски; в форме под позицией — «товар: …» с выбором из
    товаров поставщика вместо «новый товар».
19. **Деньги сделки и документы (октябрь 2026).** Итоги — как в КП, в $ и ₽ по ЦБ: «Товар», «Доставка и таможня (всё,
    кроме товара)» — перевозка, комиссия за перевод, таможенные платежи, брокер, СВХ, вознаграждение, до склада —
    и «Товар + доставка и таможня». **План статей — из сохранённого расчёта** («Рассчитать и сохранить»), он главнее
    сметы поручения (владелец загружает готовые поручения, их смета может не разобраться); чего нет в расчёте — из
    поручения (`calcPlan` в lib/finance.ts). Смету готового поручения ИИ тоже разбирает (`costs` в черновике).
    Документы сделки — карточками: номер, дата, сторона, сумма, оплата и **каждый файл отдельно** (оригинал,
    подписанный, каждая платёжка с датой — депозит, остаток, доплаты; «+ платёжка» можно много раз).
20. **Декларации / сертификаты (октябрь 2026).** Сторона декларации — изготовитель (наш поставщик): она видна у него
    (строкой наверху карточки и в документах) и у товаров. ИИ выписывает модели / артикулы (`models`), код находит в
    справочнике все товары с этими артикулами — в названии, позициях документов, ценах фабрик (`productsByArticles`) —
    и привязывает декларацию к каждому, код ТН ВЭД — из декларации. В карточке товара — блок «Декларации и
    сертификаты» (номер, изготовитель, срок, файл).
    **Декларации товары не заводят** (`replaceItems(..., { createProducts: false })`): из декларации на 46 моделей
    завелось 46 лишних товаров — владелец ругался. Модели без товара — строками декларации; товар, появившийся позже,
    подхватывает её по артикулу (`conformityIdsForProducts` — для карточки товара и сделки). На странице «Товары»
    у админа — «Удалить пустые товары» (без закупок, продаж, цен фабрик, расчётов).
21. **Несколько инвойсов и оплата на несколько счетов (октябрь 2026).** В сделке может быть несколько инвойсов —
    товары, расчёт, поручение, спецификация собираются со всех (так и было; причина жалобы — второй инвойс ИИ
    отправлял в «Новую сделку», когда у поставщика несколько сделок в работе: теперь предлагает выбрать из них,
    `shipmentOptions`). Одна платёжка может оплачивать несколько счетов (два инвойса по 25 000 — одна оплата
    50 000) или остаток инвойса в другой сделке: таблицы `payments` + `payment_allocations`, кнопка «Оплата на
    несколько счетов» в блоке «Документы» и «Одна платёжка на несколько счетов…» в форме платёжки (с «Разнести
    автоматически»). Статус оплаты разнесённых счетов — из разнесения; не разнесённое — с пометкой, что это (аванс).
    **Обычных сделок это не меняет** — владелец так просил: «одна платёжка — один счёт» работает по-старому, блок
    «Оплаты на несколько счетов», пометки на карточках и «Пояснение по оплатам.txt» в пакете для таможни
    появляются, только когда такая оплата есть (и пояснение — только если платёжка задевает другую сделку или
    часть не разнесена).
    **Разделение инвойса** (оплатили 100 рулонов, вошли 98 → инвойсы на 98 и на 2, два рулона едут со следующим
    контейнером) — бывает, но редко, стараются избегать. Владелец: «запомни, но не реализовывай». Сейчас: оба
    инвойса загружают как обычно (второй — в следующую сделку), платёжку разносят на оба.
14. **Сайт не трогать** без надобности: `/crm/` — отдельный пакет, деплоится
    отдельно (`deploy/deploy-crm.sh`), сайт байт-в-байт тот же (кроме robots.txt).

Стиль работы с владельцем: пишет по-русски коротко и эмоционально, присылает
скриншоты со стрелками. Любит, когда сначала коротко согласовали, потом сделали;
останавливает, если начали кодить большое без обсуждения. Ценит простоту и
«всё видно на одном экране». После изменений — пуш в `main` (разрешено) и
короткая инструкция, что выполнить на сервере.

## 5. Архитектура

Отдельный пакет `crm/` со своим `package.json` (не зависит от сайта).

| Слой | Технология |
|---|---|
| Сервер | Node 22, **Fastify 5**, TypeScript через **tsx** (без сборки), `@fastify/cookie`, `@fastify/multipart`, `@fastify/static` |
| БД | **PostgreSQL 16**, **Drizzle ORM** + drizzle-kit (миграции SQL в `crm/drizzle/`) |
| Пароли | `@node-rs/argon2` (argon2id) |
| DOCX | **docx-templates** (`cmdDelimiter ["{{","}}"]`) |
| Фронт | **React 19**, React Router 7 (`createBrowserRouter`, `basename /crm`), **TanStack Query 5**, Tailwind 3 (`darkMode: "class"`), Vite 8 (`base: /crm/`), TipTap 3 (база знаний) |
| Общий код | `crm/shared/*.ts` — импортируется и сервером, и фронтом (без зависимостей) |

Прод: VPS Ubuntu, nginx `location ^~ /crm/` → systemd-сервис **`bars-crm`** на
`127.0.0.1:3100`, отдаёт и API (`/crm/api/…`), и собранный SPA (`crm/web/dist`).
Сайт и обработчик заявок (`bars-lead`, порт 3000) — отдельно.

**Безопасность:** сессия — случайный токен в HttpOnly/Secure/SameSite=Lax cookie
(`path=/crm`, 30 дней), в БД хранится SHA-256 токена; CSRF-токен на сессию в
заголовке `X-CSRF-Token` + проверка Origin; лимит попыток входа по IP
(`trustProxy` только для 127.0.0.1/::1); `X-Robots-Tag: noindex` на всё,
`Disallow: /crm/` в robots.txt; журнал действий (`audit_log`); роли
`admin`/`manager`. Первый админ — CLI `npm run crm:create-admin -- --login … --name …`.

## 8. Как работают ключевые механизмы

- **Этап сделки** = `stageOf(milestones)`: первый этап, у ключевой даты которого нет факта. Хранится в
  `shipments.stage`, пересчитывается в `refreshStage` после каждого изменения дат. «Сдвинуть следующие»:
  `setMilestone(…, {plan, shift:true})` двигает плановые даты всех последующих точек без факта на ту же дельту.
  Доска: `POST /shipments/:n/stage` → `moveToStage` ставит факты сегодняшним днём (вперёд) или снимает (назад).
- **Флажки** (`flags` jsonb: ключ → дата отметки): срок флажка — плановая дата ключевой точки его этапа.
- **Расчёт цены товара** (`shared/quote.ts` → `computeQuote`, одна функция для браузера и сервера): вес / объём =
  объём партии × на единицу; доставка: контейнер — число контейнеров (явно / объём ÷ «единиц в 40HQ» / по м³ и
  весу вместимости 40HQ 68 м³ / 26 т) × ставка + сбор; сборный — платный объём max(м³, кг ÷ «кг в м³», минимум) ×
  ставка + сбор; вручную — сумма. Таможня — `calcCustoms` (стоимость + ½ доставки, пошлина по коду товара, вес — для
  ставок «за кг»). Комиссия за перевод — % от (товар + доставка). Итог = себестоимость + маржа; цена = итог ÷ объём.
  Сохранение пересчитывает на сервере по курсам, которые видел пользователь. КП: маржа строкой «Вознаграждение» или
  в стоимости товара.
- **Галочки оплат ↔ документы** (`lib/payments.ts`): balance — инвойсы поставщика сделки, freight — счета
  перевозчика (`carrier_invoice_id`, счета `carrier_id`, подрядчики carrier_*), customs_payment — ДТ. Отметили галочку
  (с датой оплаты) — документы «Оплачен» этой датой, сняли — «Не оплачен». Изменили оплату документа (PATCH) — галочка
  ставится, когда оплачены все, и снимается, если какой-то нет. Новый документ: галочка уже стоит и это первый документ
  этой оплаты (оплатили до загрузки) — сразу «Оплачен» датой галочки; иначе пересчёт (новый неоплаченный счёт снимает
  галочку). Платёжка к галочке — `POST /shipments/:n/flags/:key/proof` → файл `payment` к последнему документу оплаты.
- **Календарь** `GET /calendar` → `calendarEvents()`: плановые даты без факта, факты (как выполненные),
  неотмеченные флажки; у ключевой даты текущего этапа без плана — событие «без даты». Группировку по неделям
  делает фронт; в списке — текущий этап + всё в ближайшие 2 недели; в месяце — всё, перетаскивание.
- **Документ → сделка** (`linkToShipment`): клиент документа — из сделки; поставщик инвойса становится поставщиком
  сделки, инвойс привязывается к контракту; подрядчик → `shipment_parties`; счёт перевозчика (carrier_cn/ru) →
  перевозчик и «инвойс перевозчика» сделки. `newShipment` в `POST /documents` создаёт сделку из инвойса (этап 1).
- **Договоры подбираются сами** (`autoContracts`): действующий договор клиента по схеме (`CLIENT_CONTRACT_BY_SCHEME`),
  контракт поставщика (для ТЭУ — контракт клиента с поставщиком). Сменили клиента/схему/поставщика — подбираются заново.
- **Расчёт** `POST /shipments/:n/calc` → `computeCalc`: товары инвойсов (код — у товара, иначе у позиции; ставка из
  `tnved`), курсы — сохранённые (пошлина не «плывёт») или свежие ЦБ (`refreshRates`) → `shipments.calc`; изменение
  таможенных платежей — событие `calc` в истории. КП — `kpTemplateData` + `templates/kp.docx`.
- **Поручение** `POST /shipments/:n/order`: только схема «комиссия» и есть договор комиссии; номер = следующий
  `seq_no` по договору; позиции из всех инвойсов поставщика сделки; смета `defaultCostLines`, заполненная из
  `shipments.calc` (перевозка, брокер, СВХ, таможенные платежи, вознаграждение); в «Ходе сделки» кнопка раскрывает расчёт
  (событие `crm:open-calc`) и прокручивает к нему; DOCX —
  `GET /documents/:id/docx` (`renderOrderDocx`; свой шаблон — `CRM_UPLOAD_DIR/templates/commission_order.docx`).
- **Сертификаты в карточке**: `conformity`, привязанные к сделке **или** с позициями на товары сделки.
- **Поиск** `GET /search`: лиды, сделки (название груза, контейнер, ТН ВЭД, номер), контрагенты, документы,
  товары, страницы БЗ (full-text russian + префиксы), справочник.
- **ИИ-разбор документа**: `DocumentEditor` при выборе файла (новый документ) → `POST /ai/parse-document` →
  `applyDraft` раскладывает черновик в поля (тип, сторона — найденная или новая с реквизитами из документа, номер, дата,
  суммы, позиции, договор, сделка или «новая сделка» с названием груза). Пришли из карточки сделки — сделка не меняется,
  но если ИИ считает иначе, это видно в плашке. Контейнер/вес из документа → галочка «Записать в сделку» (PATCH сделки).
- **ИИ-чат**: модель (effort low) крутит цикл инструментов до 6 шагов; ответы инструментов ужаты (`shipmentBrief`, `pick`)
  до 16 тыс. символов, инструкция и инструменты кэшируются. Модель — `CRM_AI_MODEL` (по умолчанию `claude-haiku-5-5`).
  Расход каждого запроса — в журнале службы (`"ai":"parse"|"chat"`, `usage`).
- **Демо**: `seed --demo` (метка «демо», удаляется `--remove-demo`): лиды воронки, 3 сделки с полной цепочкой
  документов + повторные заказы на всех этапах, даты вокруг сегодняшнего дня. Всё вымышленное.

## 9. Подводные камни (наступали — не повторять)

- **Drizzle:** в single-table select `${table.id}` внутри `sql`-подзапроса рендерится как неквалифицированный
  `"id"` → писать литерально `"products"."id"`. `numeric` приходит строкой (`'1250.500'`) → `::float8` в select.
- **drizzle-kit generate** спрашивает «создать или переименовать» интерактивно → гонять через pty-скрипт,
  отвечая Enter (= create), а переименования/перенос данных дописывать в SQL руками (данные переносить
  **до** DROP). Сгенерированный SQL редактировать можно — снимок описывает только итоговую схему.
- Сгенерированная колонка `'BARS-' || number` требует `::text` (immutable).
- **docx-templates:** FOR-циклы в таблицах — отдельными строками FOR/END-FOR; переносы строк — FOR по строкам
  (`processLineBreaks` кладёт `<w:br/>` внутрь `<w:t>` — ломает).
- **React:** не объявлять компоненты внутри компонента (перемонтируются, теряют state) — см. StageTimeline.
- Тёмная тема: цвет текста на `body`, не на `html`. Выход: `removeQueries`, не `clear`.
- В контейнере Claude Code Postgres может быть остановлен → `service postgresql start`; иначе тесты молча `pass 0`.
- Пайп в `head` даёт EPIPE — безвредно. `pkill -f` с шаблоном, совпадающим с командой, убивает свой же шелл.
- **ИИ:** в контейнере Claude Code уже задан свой `ANTHROPIC_BASE_URL`, а окружение важнее `crm/.env` → для ручной
  проверки ИИ запускать сервер с `ANTHROPIC_BASE_URL=https://claude-gateway.ru/api`. Тесты ИИ не вызывают (ключи в тесте
  обнуляются). Шлюз отдаёт 429 на 3–4 параллельных запроса — SDK повторяет сам. Перед ручной проверкой убедиться, что
  на :3100 не висит старый процесс сервера (иначе новый молча не стартует, а отвечает старый код). Шлюз списывает лимит
  ≈ 3,79 × цена модели — Opus в 40 раз дороже Haiku. Haiku: путала цену за м², если она написана один раз на несколько
  строк, и считала вес сама — лечится правилами в промпте; суммы и пустые позиции проверяет код, не модель.
- **Шаблоны перевозчиков**: подписи полей бывают окружены поясняющими блоками с китайским текстом — ИИ иногда
  выбирал их; `valueCell` в коде сдвигает адрес на ячейку справа от подписи / начало объединения, «必填» и китайские
  подсказки считаются местом для значения. Строк для товаров в шаблоне ограниченное число — больше кодов ТН ВЭД → ошибка.
- **xlsxText** берёт листы по `workbook.xml.rels` (имена файлов sheetN не совпадают с порядком), скрытые пропускает.
- **Тесты расчёта** не ходят в ЦБ: `CRM_RATES_FIXED` (USD 80, EUR 90, CNY 11) и свои строки `tnved`. Вход в тестах —
  один на поздние блоки (`adminSession`), иначе 429 от лимита входов.
- **Наш блок «TO / Buyer» в чужом счёте** (реквизиты ТЛК БАРС) модель путала со стороной и ставила тип «счёт клиенту».
  Теперь: правило в промпте + код (`isOurCompany` сбрасывает сторону-нас; «счёт клиенту» от иностранной компании /
  поставщика / подрядчика → счёт подрядчика при словах о перевозке, иначе инвойс поставщика). Тест это стережёт.
- **Схемы ответа ИИ (structured outputs)**: шлюз отдаёт запросы на разные бэкенды с разными проверками — один
  не принимает `enum` вместе с `type: ["string","null"]`, другой — больше 16 полей-объединений (type-массивы, anyOf).
  Поэтому «нет значения» у строк и перечислений — `""` (в `null` превращает `emptyToNull`), `null` — только у чисел.
  Тест «схемы ответа ИИ проходят ограничения API» это стережёт. Ошибка шлюза `403 INSUFFICIENT_BALANCE` — кончился
  баланс, а не неверный ключ (`aiError` так и пишет).
- **Postgres в контейнере** мог остановиться между сессиями → `service postgresql start`, затем `db:migrate` и
  `tnved:update -- --file …` (выгрузку можно скачать `curl -L https://www.tws.by/tws/tnved/download/excel`).
- **Никогда не коммитить реальные данные клиентов** и их документы (однажды попали в тест — переписывали
  историю). Демо и тесты — только вымышленные компании/ИНН/контейнеры (`DEMU…`).

## 11. Прод и деплой

- Репозиторий на сервере: `/var/www/tlkbars/repo`; БД PostgreSQL локально; вложения
  `/var/lib/bars-crm/uploads`; бэкапы `/var/backups/bars-crm` (14 дней) + rclone-облако, cron 00:40 UTC.
- Обновление только CRM (сайт не пересобирается):
  ```bash
  cd /var/www/tlkbars/repo && git pull     # deploy-crm.sh тоже тянет main
  sudo bash deploy/deploy-crm.sh           # npm ci, build, db:migrate, restart bars-crm, health-check
  ```
  После смены структуры демо: `npm run crm:seed -- --remove-demo && npm run crm:seed -- --demo`.
- Полная установка с нуля — `crm/README.md → Деплой → Первый раз` (postgres, .env, systemd, nginx-блок, cron).
- Конфиг nginx на живом сервере старше, чем в репо (нет default-444, 404 и правил для dotfiles) — вставлять
  только блок `/crm/`, остальное не перетирать.
- **Справочник ТН ВЭД**: `deploy-crm.sh` загружает его, если пуст; ежедневно — cron
  `sudo cp deploy/cron/bars-crm-tnved /etc/cron.d/ && sudo chmod 644 /etc/cron.d/bars-crm-tnved`; вручную — `npm run crm:tnved`.
- **ИИ на сервере:** в `crm/.env` строки `ANTHROPIC_BASE_URL=https://claude-gateway.ru/api` и `ANTHROPIC_AUTH_TOKEN=…`
  (токен — у владельца, в git его нет), затем `systemctl restart bars-crm`. В nginx у `location ^~ /crm/` таймауты
  `proxy_read_timeout`/`proxy_send_timeout` 300s (разбор документа идёт до 1–2 минут).
- Логи: `journalctl -u bars-crm -n 100`; здоровье: `curl 127.0.0.1:3100/crm/api/health`.
